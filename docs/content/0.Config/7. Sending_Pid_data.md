# Types of PIDs Destination
There are four methods to send PID data to Home Assistant. Each method handles memory, network traffic, and Home Assistant integration entirely differently. Here is the deep dive into exactly how they work under the hood, along with the pros and cons of each.

---

### 1. Configured Destinations (The Global Batch Engine)

**How it works:** When you set a PID parameter's destination type to `Default`, the WiCAN stops treating it as an individual entity. Instead, a background process (`autopid_data_update`) continuously sweeps up the latest values of all `Default` PIDs and packs them into one massive global JSON dictionary.
A separate background task then looks at your "Configured Destinations" list and pushes this massive JSON snapshot out via MQTT or HTTP based on the "Cycle" timer you configured (e.g., every 5 seconds).

**Pros:**

* **Network Efficiency:** Highly efficient for your Wi-Fi network. Instead of sending 50 separate messages, it sends one combined payload.
* **Multi-Routing:** You can send this exact same snapshot to multiple places at once (e.g., send one copy to Home Assistant via MQTT, and another copy to A Better Routeplanner via HTTP).
* **Easy UI Management:** You don't have to type out individual MQTT topics for every single PID.

**Cons:**

* **Delayed / Not Real-Time:** Because it relies on the "Cycle" timer, data is buffered. If the ECU responds instantly, the data just sits in RAM until the 5-second timer expires.
* **Massive Payloads:** Home Assistant receives a giant JSON string that it has to unpack using JSON value templates (`value_template: "{{ value_json.RPM }}"`).

---

### 2. Individual MQTT Topics (`MQTT_Topic`)

**How it works:**
When you set a PID parameter to `MQTT_Topic` and give it a specific path (e.g., `car/engine/rpm`), it completely bypasses the global batch engine. If you look at `publish_parameter_mqtt()` in the C code, the exact millisecond the WiCAN parses the response from the car's ECU, it fires a tiny, isolated MQTT payload directly to your broker.

**Pros:**

* **Ultra-Low Latency:** This is true real-time, event-driven data. As fast as the car can spit out the RPM, the WiCAN fires it to Home Assistant.
* **"On Change" Filtering:** You can check the "OnChg" box in the UI, and the C code will silently drop the message if the value hasn't changed since the last poll, drastically cutting down on useless data.
* **Easy HA Integration:** Extremely simple to set up in Home Assistant's `configuration.yaml` because each sensor gets its own dedicated topic.

**Cons:**

* **Network Spam:** If you are polling 20 PIDs 10 times a second, the WiCAN is firing 200 individual MQTT messages per second over your Wi-Fi.
* **Tedious Setup:** You have to manually type out a unique MQTT topic for every single parameter in the WiCAN UI.

---

### 3. Vehicle Group Topics (`MQTT_Grp`)

**How it works:**
This is the newest hybrid feature in the firmware. Inside a Vehicle Group, you define a master `Group MQTT Topic` (e.g., `car/group/engine_running`). You then set the PIDs inside that group to `MQTT_Grp`.
The code polls the car for all the PIDs in that specific group. The moment the group finishes its batch, it aggregates just those specific PIDs into a mini-JSON snapshot and fires it to the group topic.

**Pros:**

* **The "Goldilocks" Balance:** It prevents the network spam of individual topics, but it doesn't suffer from the timer delays of Configured Destinations. It publishes the moment the batch is done.
* **Contextual Payloads:** You can group related data together. For example, Home Assistant receives one payload containing Voltage, RPM, and Coolant Temp all at the exact same timestamp.
* **Adaptive Logic:** Because the group itself can be turned on/off based on conditions (e.g., "Engine Running"), this data completely stops transmitting when the car is off, saving battery.

**Cons:**

* **Requires Group Architecture:** You have to migrate your flat PIDs into the newer Group logic.
* **Template Parsing:** Like the global destination, Home Assistant still has to parse a JSON dictionary to extract the values (though a much smaller one).

---

### 4. Webhooks (Home Assistant Integration)

**How it works:**
This method completely bypasses MQTT. In the "Automate" tab, you enable the Webhook and point it to an HTTP URL generated by the official WiCAN Home Assistant Integration. A dedicated C task (`autopid_webhook_task`) takes the global JSON snapshot (all your `Default` PIDs), packages it alongside the WiCAN's system status (Wi-Fi strength, voltage, sleep state), and fires it as an HTTP POST request directly to your Home Assistant server on a set interval (usually 60 seconds).

**Pros:**

* **Zero Infrastructure:** You do not need to install, secure, or maintain an MQTT Broker (like Mosquitto) on your network.
* **Auto-Discovery:** The WiCAN Home Assistant integration automatically reads the webhook payload and creates all the entities/sensors in your HA dashboard for you. It's essentially plug-and-play.
* **Smart Diffing:** You can set "WebHook Data Mode" to "Changed Values Only", and the WiCAN will only send data that has actually updated since the last HTTP post.

**Cons:**

* **Heavy Network Overhead:** HTTP POST requests require significantly more network overhead (headers, handshakes, TLS setup) than lightweight MQTT publishes.
* **Slow Updates:** Because of the HTTP overhead, webhooks are usually scheduled to run every 30 to 60 seconds. It is strictly for slow telemetry (like Battery Level or Odometer), not fast telemetry (like RPM or Speed).
